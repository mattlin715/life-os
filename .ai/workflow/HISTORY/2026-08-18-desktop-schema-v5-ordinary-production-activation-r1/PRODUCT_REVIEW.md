## Mission Interpretation

Promote the already Founder-reviewed isolated desktop schema-v5 activation and typed runtime contract into the ordinary `com.lifeos.app` desktop build, while preserving explicit per-operation migration, exact verified backup/restore evidence, schema-v4 compatibility, and every existing Product Harness boundary. Automated work remains synthetic/disposable. The real ordinary Founder profile is excluded until a later explicit Phase B decision.

## Problem Statement

Life OS has promoted private evidence for schema-v5 DDL, migration, restart classification, backup/restore, and typed runtime parity, but the ordinary identity still starts through schema v4. Copying Candidate behavior wholesale would risk identity confusion, duplicated authority, silent migration, or accidental contact with the Founder's real profile. The product needs one shared desktop activation core plus an ordinary policy adapter and a review-only package whose ordinary identity is truthful.

## User Value

The change makes the durable append-only lifecycle foundation reachable in the ordinary desktop while preserving local control: existing users see a clear migration-required state, can cancel without mutation, and can authorize one verified-backup migration; new users receive exact v5 without an intermediate exposed v4 database. It improves integrity and reversibility rather than model authority or engagement.

## Product Constraints

Opening the app or reading disclosure is never migration authorization. Missing-profile initialization is allowed only in the v5-capable build and must publish exact verified v5. Existing exact v4 must remain unchanged until an explicit action. Newer, malformed, ambiguous, sidecar-active, or contradictory states block writes. The current reflection journey, historical retrieval, and consent flow remain behaviorally unchanged.

## Evidence And Provenance Constraints

The accepted v5 authority, immutable revisions, review/lifecycle events, exact dependencies, guarded v4 projection, content purge, tombstones, migration receipt, and two-manifest predicate are reused. No raw content, personal paths, credentials, or machine identity may enter package manifests or workflow evidence.

## Historical Context Constraints

ADR-0009 behavior remains byte- and contract-compatible: exact eligible sources, current revisions, packet digest, per-generation/per-purpose consent, successful transmission, actual-use provenance, and cascade semantics. No new retrieval, whole-history, summary, or Phase 4 interpretation is introduced.

## Consent Constraints

Migration consent is a separate explicit local operation action. It is not provider-use consent and cannot be persisted as blanket authorization. Cancel creates no backup, operation evidence, DDL, receipt, or version change. Historical provider consent remains unchanged.

## AI-Role Constraints

No model prompt, output contract, provider, ContextPacket, inference depth, sensitive-inference policy, or hypothesis semantics change. Storage evolution must not make AI artifacts more authoritative.

## Privacy Constraints

Automated and packaged review use disposable roots only. The ordinary Founder profile must not be opened, hashed, copied, inspected, migrated, or printed before a separate Phase B authorization. Backups are sensitive local copies, exact-owned, retained at most 30 days, explicitly deletable, and unable to reverse provider receipt.

## User-Agency Constraints

The user controls migration, cancel, restore, and delete-now independently. Failures remain visible and no success is claimed without exact durable evidence. An older v4 binary must refuse v5 writes. There is no silent repair or schema decrement.

## Acceptance Criteria

1. Ordinary v5-capable startup distinguishes missing, exact v4, exact v5, blocked, and recovery-required states before writable initialization.
2. Missing ordinary disposable profile initializes exact verified v5; existing v4 is not silently migrated.
3. Cancel is no-op; explicit migration creates one verified backup and exact v5.
4. Restart classifies exact durable evidence without autonomous action.
5. Every currently reachable mutation uses typed v5 Rust routing after cutover with exact postconditions and stale refusal.
6. Backup retention, delete-now, and restore are explicit, exact-owned, and fail closed.
7. Existing Founder Candidate remains functional through the same core.
8. Three-language UI states are equivalent and preserve the normal reflection flow.
9. Version/config/package contracts prove ordinary identifier, 0.3.0, review-only title, no Android, and content-free manifest.
10. Focused tests, Clippy, package tests, and `scripts/verify.ps1` pass.
11. No automated command accesses either real ordinary or Founder profile.
12. The sprint stops before installation at one-step Founder Phase A review.

## Risks

- Ordinary identity makes accidental installation/profile contact materially higher risk; build scripts must never install or launch.
- Multiple SQLite connections or sidecars can invalidate quiescence; unknown must block rather than checkpoint.
- Refactoring Candidate code can create Founder regression or two competing state machines.
- Version and feature-gate drift can compile a frontend that requests unavailable commands.
- Old binaries may attempt guarded v4 projection writes; v5 triggers and explicit manual refusal evidence remain required.
- Backup deletion and Windows replacement can produce ambiguous outcomes; only exact durable evidence may classify success.
- A broad UI rename could accidentally alter Product Harness copy; migration disclosure must remain isolated.
